01

Data Parallelism

Every worker (a GPU, or a whole machine) holds a full copy of the model and gets its own share of each batch. Each runs the forward and backward passes on its share; then the workers’ gradients are averaged and every copy takes the same optimiser step, so the copies stay identical.

worker 1: windows 1–4 → g1
worker 2: windows 5–8 → g2
…
→
all-reduce: ¼∑ gi
→
same step everywhere

The average of \(W\) workers’ mean gradients over \(B/W\) windows each is exactly the mean gradient over the whole batch: data parallelism changes where the arithmetic happens, not what it computes. Checked on the model: four simulated workers with four windows each end the default run at 2.299304; one worker with sixteen windows at 2.299304 (the additions happen in a different order, so the last bits differ). More workers means a bigger batch per step, and the critical batch (deck 05) says how far that helps.

02

The Ring All-Reduce, Step by Step

Averaging the gradients is a collective called an all-reduce: every worker starts with its own vector and ends with the sum. The ring cuts each vector into \(p\) chunks. In \(p-1\) reduce-scatter steps each worker passes one chunk to its neighbour, which adds it to its own; then each worker holds the finished sum of one chunk. In \(p-1\) all-gather steps the finished chunks go round until everyone has all of them.

Orange: a chunk just received. Green: a finished sum of all four. Each worker sends \(2(p-1)/p\) of its vector, never more than twice it however many workers there are, which is the least any all-reduce can send (Patarasuk & Yuan 2009). What grows with the ring is the number of steps, \(2(p-1)\), each paying a link’s latency.

03

The α–β Link Model

Sending \(n\) bytes over a link costs \(\alpha + n/B\): a fixed latency and the bytes over the bandwidth. For \(p\) ranks and a vector of \(M\) bytes:

$$\begin{gathered} t_{\text{ring all-reduce}} = 2(p-1)\,\alpha + 2\,\tfrac{p-1}{p}\,\tfrac{M}{B} \\ t_{\text{reduce-scatter}} = t_{\text{all-gather}} = (p-1)\,\alpha + \tfrac{p-1}{p}\,\tfrac{M}{B} \\ t_{\text{tree, not pipelined}} = 2\,\lceil \log_2 p \rceil\,(\alpha + M/B) \end{gathered}$$

H100 figures as the site’s systems model uses them: NVLink 900 GB/s total (450 each way) and 989 TFLOP/s dense BF16 from the H100 SXM datasheet; 400 Gb/s per GPU on the network (Llama 3, §3.3.1). The WAN option is a 100 GbE link (12.5 GB/s) with the network’s latency, an illustration for deck 12.

05

All-Gather, and Why Its Bytes Grow

An all-gather is the second half of a ring all-reduce on its own: every worker contributes a piece and ends up with everyone’s pieces. Inside an all-reduce the pieces are chunks of one sum, added on the way. That only works when every worker’s vector has the same layout, as dense gradients do.

Same layout: all-reduce

Bytes each worker sends: \(2\,\tfrac{p-1}{p}M\), below twice the vector however large \(p\) grows.

Different layouts: all-gather

If each worker sends something different (say the 1 value in 16 it judged most important, with its position), the pieces cannot be added as they pass: each must arrive whole. Each worker sends its own piece and forwards the others: \((p-1)\) pieces, growing with the number of workers.

That is why compressing a gradient 16-fold saves far less than 16-fold on the wire once there are many workers: the central point of deck 12.

06

Payload and Bytes on the Wire

Two numbers describe a sync. The payload is what a worker originates: its dense gradient is 2 bytes per parameter in BF16 (deck 08), so LLaMA 7B’s is 13.5 GB. The wire bytes are what it actually sends in the collective, forwarding included:

$$\begin{gathered}\text{all-reduce: } 2\,\tfrac{p-1}{p}\times\text{payload} \\ \text{all-gather (compressed): } (p-1)\times\text{payload}\end{gathered}$$

Among 64 GPUs a ring all-reduce has each GPU send 26.5 GB per step. Link time follows the wire bytes, not the payload; the Compute in Transit results site quotes both, and so does deck 12.

07

ZeRO and FSDP: Stop Every Worker Holding Everything

Plain data parallelism replicates all 16 bytes per parameter on every worker (deck 09). ZeRO (Rajbhandari et al. 2020) shards them across the \(d\) data-parallel workers: stage 1 the optimiser states, stage 2 the gradients too (a reduce-scatter instead of an all-reduce), stage 3 the weights themselves, all-gathered layer by layer just before use. PyTorch’s FSDP (Zhao et al. 2023) is stage 3.

$$\begin{aligned}\text{stage 0: } & (2 + 2 + K)\Psi \\ \text{1: } & 4\Psi + K\Psi/d \\ \text{2: } & 2\Psi + (2 + K)\Psi/d \\ \text{3: } & (2 + 2 + K)\Psi/d\end{aligned}$$

08

Step Time = Compute + Communication, and Overlap

A data-parallel step costs the forward and backward compute plus the gradient sync. Nothing forces the sync to wait for the whole backward pass: the last layer’s gradients are ready first, so frameworks send them in buckets while the backward pass works on earlier layers (PyTorch DDP, Li et al. 2020). When the communication fits inside the remaining backward pass it costs nothing extra.

Nothing overlapped

Compute 1.64 s + all-reduce 0.53 s = 2.17 s per step; MFU 35.7%.

All-reduce hidden

1.64 s per step; MFU 47.3%, the model’s ceiling (its fitted matrix-multiply efficiency η = 0.473).

One data-parallel step of LLaMA 7B on 64 H100s with 1,048,576 tokens, by the systems model (results.md §11b). Over a much slower link the communication outgrows the compute and no overlap can hide it: deck 12.

09

MFU: Model FLOPs Utilisation

$$\text{MFU} = \frac{D\,(6N + 12\,L\,H\,Q\,T)}{t \cdot n \cdot P}$$

The floating-point operations the model needs per second (about \(6N\) per token for \(N\) parameters, plus attention’s \(12LHQT\), counted from the tokens \(D\) actually processed in time \(t\)) divided by the peak \(P\) of \(n\) devices (Chowdhery et al. 2022, PaLM, §4.1 and App. B). Recomputed activations don’t count, so MFU compares systems fairly; counting them gives hardware FLOPs utilisation.

What to Take Away

  • Data parallelism = full copies + an all-reduce of the gradients; same maths as one big batch.
  • The ring sends \(2(p-1)/p\) of the vector per worker: bandwidth-optimal, latency \(2(p-1)\alpha\).
  • Different layouts (compressed vectors) need an all-gather, whose bytes grow with \(p\).
  • Count wire bytes, not payload, for link time.
  • ZeRO / FSDP shard the 16 bytes per parameter; stage 3 costs 1.5× the traffic.
  • Overlap hides the sync behind the backward pass; MFU measures what is left.
